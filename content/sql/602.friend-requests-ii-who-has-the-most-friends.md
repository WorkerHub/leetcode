## 题目描述

表：`RequestAccepted`

```
+----------------+---------+
| Column Name    | Type    |
+----------------+---------+
| requester_id   | int     |
| accepter_id    | int     |
| accept_date    | date    |
+----------------+---------+
```

`(requester_id, accepter_id)` 是这张表的主键。
这张表包含发送好友请求的人的 ID，接收好友请求的人的 ID 以及好友请求通过的日期。

写一个 SQL 查询，找出拥有最多的好友的人和他拥有的好友数目。

生成的测试用例保证拥有最多好友数目的只有 1 个人。

查询结果格式如下例所示。

**示例 1：**

```
输入：
RequestAccepted 表：
+--------------+-------------+-------------+
| requester_id | accepter_id | accept_date |
+--------------+-------------+-------------+
| 1            | 2           | 2016/06/03  |
| 1            | 3           | 2016/06/08  |
| 2            | 3           | 2016/06/08  |
| 3            | 4           | 2016/06/09  |
+--------------+-------------+-------------+

输出：
+----+-----+
| id | num |
+----+-----+
| 3  | 3   |
+----+-----+

解释：
编号为 3 的人是编号为 1，2 和 4 的人的好友，所以他总共有 3 个好友，比其他人都多。
```

**进阶：**在真实世界里，可能会有多个人拥有好友数相同且最多，你能找到所有这些人吗？

## 解题思路

这道题的核心是理解**好友关系是双向的**：
- 如果 A 向 B 发送请求且被接受，那么 A 和 B 互为好友
- 因此，`requester_id` 和 `accepter_id` 都需要统计

**核心思路：**

1. **合并双向关系**：将 requester_id 和 accepter_id 统一为一个字段
2. **分组统计**：按人员 id 分组，统计好友数量
3. **找出最大值**：找到好友数最多的人

**三种实现方法：**

**方法一：UNION ALL + GROUP BY（推荐）**
- 使用 UNION ALL 合并请求者和接受者
- GROUP BY 统计每个人的好友数
- ORDER BY + LIMIT 找出最多的

**方法二：子查询**
- 先统计所有人的好友数
- 再查询好友数等于最大值的记录

**方法三：窗口函数（适用于找出所有最多好友的人）**
- 使用 DENSE_RANK() 标记排名
- 筛选排名第一的所有人

## SQL 代码实现

### 方法一：UNION ALL + 聚合（最简洁）⭐

```sql
SELECT id, COUNT(*) AS num
FROM (
    -- 作为请求者的好友关系
    SELECT requester_id AS id FROM RequestAccepted
    UNION ALL
    -- 作为接受者的好友关系
    SELECT accepter_id AS id FROM RequestAccepted
) AS all_friends
GROUP BY id
ORDER BY num DESC
LIMIT 1;
```

**优化版本（处理并列情况）：**

```sql
WITH friend_counts AS (
    SELECT id, COUNT(*) AS num
    FROM (
        SELECT requester_id AS id FROM RequestAccepted
        UNION ALL
        SELECT accepter_id AS id FROM RequestAccepted
    ) AS all_friends
    GROUP BY id
)
SELECT id, num
FROM friend_counts
WHERE num = (SELECT MAX(num) FROM friend_counts);
```

### 方法二：子查询（经典写法）

```sql
SELECT id, SUM(cnt) AS num
FROM (
    SELECT requester_id AS id, COUNT(*) AS cnt
    FROM RequestAccepted
    GROUP BY requester_id
    
    UNION ALL
    
    SELECT accepter_id AS id, COUNT(*) AS cnt
    FROM RequestAccepted
    GROUP BY accepter_id
) AS temp
GROUP BY id
ORDER BY num DESC
LIMIT 1;
```

### 方法三：窗口函数（处理并列第一）⭐

```sql
WITH friend_counts AS (
    SELECT id, COUNT(*) AS num
    FROM (
        SELECT requester_id AS id FROM RequestAccepted
        UNION ALL
        SELECT accepter_id AS id FROM RequestAccepted
    ) AS all_friends
    GROUP BY id
),
ranked AS (
    SELECT id, num,
           DENSE_RANK() OVER (ORDER BY num DESC) AS rnk
    FROM friend_counts
)
SELECT id, num
FROM ranked
WHERE rnk = 1;
```

### 方法四：使用 CTE 增强可读性

```sql
WITH all_relations AS (
    -- 合并所有好友关系（双向）
    SELECT requester_id AS person_id FROM RequestAccepted
    UNION ALL
    SELECT accepter_id AS person_id FROM RequestAccepted
),
friend_count AS (
    -- 统计每个人的好友数
    SELECT person_id AS id, COUNT(*) AS num
    FROM all_relations
    GROUP BY person_id
)
SELECT id, num
FROM friend_count
ORDER BY num DESC
LIMIT 1;
```

## 复杂度分析

### 方法一（UNION ALL）
- **时间复杂度**：O(n log n)，其中 n 是记录数，主要开销在排序
- **空间复杂度**：O(n)，UNION ALL 结果集

### 方法三（窗口函数）
- **时间复杂度**：O(n log n)，窗口函数需要排序
- **空间复杂度**：O(n)

**性能对比：**
- 方法一最简洁高效（单人最多情况）
- 方法三适合处理并列第一的情况
- 所有方法在小数据集上性能差异不大

## 关键点总结

1. **好友关系是双向的**：requester 和 accepter 都要统计
2. **UNION ALL vs UNION**：使用 UNION ALL 保留重复（一个人可以有多个好友），性能更好
3. **处理并列情况**：题目说只有一个最多，但实际可能有并列，需要考虑
4. **聚合顺序**：先 UNION ALL 再 GROUP BY，逻辑清晰
5. **LIMIT 1 的使用**：题目保证唯一，可以直接用 LIMIT 1

## 易错点

1. **忘记统计双向关系**：
   ```sql
   -- ❌ 错误：只统计了作为请求者的情况
   SELECT requester_id AS id, COUNT(*) AS num
   FROM RequestAccepted
   GROUP BY requester_id
   ```

2. **使用 UNION 而非 UNION ALL**：
   ```sql
   -- ❌ 错误：UNION 会去重，导致统计错误
   SELECT requester_id AS id FROM RequestAccepted
   UNION  -- 应该用 UNION ALL
   SELECT accepter_id AS id FROM RequestAccepted
   ```

3. **分组前就聚合**：
   ```sql
   -- ❌ 错误：先 COUNT 再 UNION，逻辑错误
   SELECT requester_id, COUNT(*)
   FROM RequestAccepted
   GROUP BY requester_id
   UNION ALL
   SELECT accepter_id, COUNT(*)
   FROM RequestAccepted
   GROUP BY accepter_id
   -- 这样会把两边的 COUNT 值合并，而非合并后再 COUNT
   ```

4. **没有处理并列情况**：题目说保证唯一，但最好能处理多人并列的情况

## 学习建议

**新手学习路径：**

1. **理解双向关系**：
   - 好友关系是对称的：A 是 B 的好友，B 也是 A 的好友
   - 需要同时统计作为 requester 和 accepter 的次数

2. **UNION vs UNION ALL**：
   - `UNION`：去重，会合并相同的行
   - `UNION ALL`：不去重，保留所有行（性能更好）
   - 本题需要保留重复，因为要统计总数

3. **循序渐进**：
   - 第一步：列出所有 requester_id（作为好友的一方）
   - 第二步：列出所有 accepter_id（作为好友的另一方）
   - 第三步：合并并统计每个人出现的次数
   - 第四步：找出出现次数最多的

4. **推荐方法**：
   - 初学者：方法一，逻辑清晰，代码简洁
   - 进阶：方法三，掌握窗口函数，处理更复杂的场景

5. **验证思路**：
   - 手动计算示例数据：
     - ID 1：作为 requester 2次 → 2个好友（2, 3）
     - ID 2：作为 requester 1次，accepter 1次 → 2个好友（1, 3）
     - ID 3：作为 accepter 2次，requester 1次 → 3个好友（1, 2, 4）
     - ID 4：作为 accepter 1次 → 1个好友（3）
   - 因此 ID 3 有最多好友（3个）

**实战技巧：**
- 遇到双向关系问题，首先想到 UNION ALL
- 使用 CTE 可以让 SQL 更易读易维护
- 注意题目是否保证唯一，决定用 LIMIT 还是子查询
